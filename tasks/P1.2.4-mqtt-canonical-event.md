# P1.2.4 — MQTT canonical RecognitionEvent boundary

Status: ACTIVE — adapter review pending integration

## Objective
Use the existing MQTT v1 transport as the device-facing adapter while preventing a second biometric event schema. A confirmed biometric decision must originate as the canonical `RecognitionEvent`; MQTT is transport only.

## Existing implementation
- `src/devices/mqtt_adapter.py` already provides MQTT v1 command/state/event topics.
- MQTT uses QoS 1 for commands/events and retained availability/state.
- Existing MQTT command deduplication is device/request scoped and currently defaults to TTL memory.
- `requirements.txt` pins `paho-mqtt>=2.1.0,<3.0.0`.

## Required architecture
Recognition pipeline -> canonical RecognitionEvent -> durable PostgreSQL event boundary -> MQTT publish.

MQTT must never create or alter `person_id`, similarity, quality, liveness, or confirmation state.

Recommended event topic: `face/v1/devices/{device_id}/event`.
Payload must be the canonical RecognitionEvent JSON or a versioned envelope containing exactly that event; do not maintain a second biometric field contract.

## Verification
- Publish a valid canonical event and decode it back losslessly.
- Invalid/missing biometric fields are rejected before publish.
- MQTT redelivery does not execute an actuator action twice.
- PostgreSQL remains the durable idempotency boundary; in-memory MQTT dedupe is only an optimization.
- No embedding vectors are published over MQTT by default.
- TLS configuration remains supported for broker connections.
