# P1.1.6 — Real PostgreSQL/pgvector execution matrix

## Status
ENVIRONMENT-GATE IMPLEMENTED — benchmark execution pending a reachable authorized PostgreSQL/pgvector instance.

## Goal
Produce the first real execution receipt for person-level vector retrieval and decide whether HNSW filtering, candidate-first reranking, or one-vector-per-person is safe enough for production.

## Fresh research basis
pgvector 0.8.x supports iterative HNSW scans for filtered approximate search. `strict_order` preserves distance ordering; `relaxed_order` can improve recall at the cost of slightly relaxed ordering. The upstream project also exposes `hnsw.max_scan_tuples` and `hnsw.scan_mem_multiplier` to control iterative scan cost. See the upstream README: https://github.com/pgvector/pgvector

For this face-recognition workload, filtering by `model_version` and active `person_id` status must therefore be treated as a correctness dimension, not merely a SQL optimization.

## Environment gate
Run:

    python tools/inspect_pgvector_environment.py

The script is read-only and reports:
- PostgreSQL version
- pgvector extension version
- `hnsw.ef_search`
- `hnsw.iterative_scan`
- `hnsw.max_scan_tuples`
- `hnsw.scan_mem_multiplier`
- relevant HNSW indexes

It returns blocked status instead of inventing a benchmark result when `PG_DSN` is absent, the DB is unreachable, or pgvector is not installed.

## Required matrix
For each gallery size 100, 1,000, 10,000 persons and templates/person 1, 3, 10, 30:

1. exact person-level oracle
2. production person-level query
3. HNSW `ef_search`: 40, 80, 160, 320
4. `iterative_scan`: off, strict_order, relaxed_order
5. candidate-first with oversample 10x, 20x, 50x
6. candidate-first + exact template rerank
7. one-vector-per-person prototype
8. prototype + exact template rerank

Where filtered recall is stressed, additionally record `hnsw.max_scan_tuples` and `hnsw.scan_mem_multiplier` rather than silently changing them.

## Metrics
Every configuration must report:
- recall@1/@5/@10 by `person_id`
- missing-person rate
- duplicate `person_id` rate
- p50/p95/p99 latency
- timed sample count
- PostgreSQL version
- pgvector version
- query/index configuration

Use the deterministic query seed and repeated timing protocol from P1.1.5.

## Correctness gates
- Exact oracle is independent of ANN retrieval.
- Recognition threshold/margin is never changed to hide retrieval misses.
- Active and model-version filtering stay enabled.
- Candidate reranking is measured separately from raw ANN retrieval when the benchmark claims database-only latency.
- No production tables may be truncated or overwritten by the benchmark.
- Synthetic vectors are evidence for retrieval mechanics only, not biometric recognition accuracy.

## Decision rule
Do not change the production schema unless the candidate architecture is no worse than the current person-level template search on recall and has a measured latency/memory benefit under the same workload.

A latency win with lower recall is a rejection, not a trade-off to hide in the recognition threshold.

## Next step
After the real execution receipt, lock the retrieval architecture and move to multi-frame tracking/confirmation. If filtered HNSW remains recall-fragile, evaluate partitioning/partial indexes or an alternate vector backend before increasing recognition complexity.
