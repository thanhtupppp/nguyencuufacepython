# P1.2.4.2 — MQTT broker integration verification

## Goal
Verify the canonical `RecognitionEvent` bridge against a real MQTT broker. This is the final gate before closing P1.2.4.

## Why this gate exists
MQTT QoS 1 is at-least-once: duplicates are possible, so the application must remain idempotent even when the same recognition event is delivered more than once. The event identity is `event_id`; MQTT packet identifiers are not an application-level identity.

## Verification
1. Start a real MQTT broker with TLS/authentication matching the existing adapter contract.
2. Start the recognition service/bridge and a subscriber using the canonical event topic.
3. Publish one `RECOGNITION_CONFIRMED` event.
4. Assert the subscriber receives the exact `event_id`, `person_id`, model/embedding versions and biometric gate values.
5. Force reconnect/redelivery and assert duplicate delivery does not create a second downstream action.
6. Assert non-confirmed states are rejected by the bridge.
7. Assert embedding/image fields are absent from the MQTT envelope.

## Acceptance criteria
- Real broker publish/subscribe passes.
- QoS 1 is retained for the event path.
- Duplicate delivery cannot create duplicate action when the durable idempotency boundary is present.
- Canonical event fields survive serialization unchanged.
- No embedding or image is transported over MQTT.
- Failure/reconnect behavior is documented.

## Current status
