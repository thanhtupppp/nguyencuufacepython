# P0.4.17 — Template-level vs one-vector-per-person prototype benchmark

## Objective

Benchmark two person-level retrieval representations before any production architecture change:

1. **Template-level**: keep every enrollment embedding in `face_embeddings`, retrieve template candidates, then reduce to the best score per `person_id`.
2. **One-vector-per-person prototype**: derive one normalized prototype per person from that person's enrollment embeddings and search prototypes.

The benchmark must use the same frozen ArcFace model/version and the same leakage-safe query protocol. No recognition threshold may be tuned to compensate for retrieval differences.

## Prototype definition

The initial candidate prototype is a quality-weighted centroid:

- L2-normalize each 512-D embedding.
- Weight by `quality_score` (minimum positive floor required).
- Compute weighted mean per `person_id`.
- L2-normalize the resulting centroid.

This is a **benchmark candidate**, not a production decision.

## Required measurements

- Recall@1/@5/@10 against a leakage-safe template-level exact reference.
- False retrieval / wrong-person rate.
- Unknown-query behavior using held-out identities where available.
- Similarity distributions for genuine vs impostor queries.
- Top-1 score and top-1/top-2 margin.
- p50/p95/p99 latency.
- Gallery size: persons and templates/person.
- Active-person and model-version filtering.
- PostgreSQL/pgvector version.
- HNSW settings when ANN is used.

## Dataset protocol

- At least 2 templates/person for leakage-safe leave-one-out queries.
- Query template must never be part of the template gallery used by the reference search.
- For prototype search, the query's source template must be excluded when constructing that person's prototype; otherwise the prototype benchmark leaks the query into the target representation.
- Keep person IDs disjoint for any unknown-query evaluation.

## Acceptance gates

Do not change production architecture unless the prototype candidate demonstrates comparable or better recall and false-match safety, while meeting the required latency target.

A faster prototype is not sufficient if it increases wrong-person retrieval or collapses the top-1/top-2 margin.

## Next step

After real execution, select one of:

- retain template-level person grouping;
- adopt one-vector-per-person prototype;
- keep both, using prototype retrieval for candidate generation followed by template verification.

The third option is allowed only if measured recall and latency justify the added complexity.
