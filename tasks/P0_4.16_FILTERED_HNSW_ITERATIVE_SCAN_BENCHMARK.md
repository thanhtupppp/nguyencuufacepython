# P0.4.16 — Filtered HNSW iterative-scan benchmark

## Goal
Measure whether pgvector HNSW iterative scans recover person-level retrieval under selective filters without changing the ArcFace recognition threshold.

## Research basis
pgvector documents that approximate indexes can return fewer rows when filters are applied after the index scan. Since pgvector 0.8.0, HNSW supports `off`, `strict_order`, and `relaxed_order` iterative scans. The benchmark must measure all three against exact-search ground truth.

## Scope
Run the same leakage-safe queries and compare:
- exact SQL ground truth;
- HNSW `iterative_scan=off`;
- HNSW `iterative_scan=strict_order`;
- HNSW `iterative_scan=relaxed_order`.

Sweep:
- `hnsw.ef_search`: 40, 80, 160, 320;
- `hnsw.max_scan_tuples`: 20000, 50000;
- candidate pool: 50, 100, 300;
- active-person selectivity: full gallery plus filtered subsets where available.

## Correctness invariants
- query embedding is excluded from its own gallery;
- at least two templates/person;
- model_version is fixed;
- person-level grouping occurs after template retrieval;
- exact search remains the ground truth;
- no recognition threshold is tuned from ANN results.

## Metrics
- query-person Recall@1/@5/@10;
- exact-vs-ANN Top-K agreement;
- shortfall rate (fewer than K eligible persons returned);
- p50/p95/p99 latency;
- pgvector version;
- scan mode and parameters;
- candidate pool;
- eligible persons and embeddings.

## Completion criteria
1. Benchmark runs against real PostgreSQL/pgvector with real ArcFace embeddings.
2. Every configuration records recall and latency.
3. Any filtered-query shortfall is visible rather than silently treated as UNKNOWN.
4. Production HNSW mode is not selected until results are compared with exact search.

## Next
If iterative scan materially closes the recall gap, benchmark template-level HNSW against a one-vector-per-person prototype. Otherwise keep exact search or redesign the index/filter strategy before production rollout.
