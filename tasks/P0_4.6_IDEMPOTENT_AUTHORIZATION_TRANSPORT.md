# P0.4.6 — Idempotent authorization transport

## Status
IMPLEMENTED — execution receipt pending.

## Objective
Prevent duplicate physical actions when an authorized face event is retried or delivered more than once over MQTT, HTTP, or WebSocket.

## Design
`authorization_event_id(camera_id, frame_index, track_id, person_id)` produces a deterministic SHA-256 idempotency key.

The action/transport layer must:
- publish the same event ID on retries;
- persist or atomically deduplicate consumed event IDs at the action boundary;
- never execute a second physical action for an already-consumed event ID;
- keep `camera_id`, `track_id`, and `person_id` explicit in the event envelope.

The event ID is not a biometric identifier and does not replace `person_id`.

## Verification
1. Unit-test deterministic ID generation.
2. Replay the same authorized event N times through each transport adapter.
3. Assert exactly one action execution.
4. Replay the same event after reconnect/retry.
5. Assert duplicate delivery is acknowledged/ignored without a second action.
6. Verify a changed frame/track/person produces a different event ID.

## Completion criteria
- focused unit tests pass;
- transport adapters expose the idempotency key;
- action executor has an atomic deduplication boundary;
- duplicate delivery cannot trigger a second action;
- replay receipt records transport, event ID, execution count, and result.
