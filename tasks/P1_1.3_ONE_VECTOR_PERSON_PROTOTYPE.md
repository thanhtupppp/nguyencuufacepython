# P1.1.3 — One-vector-per-person prototype benchmark

## Status
HARNESS_READY — real PostgreSQL/pgvector execution receipt pending.

## Goal
Evaluate one normalized prototype embedding per person as a retrieval candidate. This is a benchmark candidate only; it must not replace template-level enrollment until accuracy and safety gates pass.

## Prototype rule
For each person, compute the normalized mean of that person's enrollment embeddings. Store exactly one prototype row per person in a temporary benchmark table. Preserve the original multi-template gallery for the exact person-level oracle.

## Verification
Compare `prototype` and `prototype_rerank` against the exact best-template-per-person reference. Measure recall@1/@5/@10, missing-person rate, duplicate person_id rate, p50/p95 latency, and sensitivity to 1/3/10/30 templates per person. Test active-person filtering and model-version isolation in the reference path. For prototype retrieval, candidate oversampling must be explicit; prototype_rerank must rerank selected people using their original enrollment templates before final top-K.

## Safety rule
Do not use prototype similarity as the final recognition score until validated. A mean prototype can blur multi-modal enrollment distributions and can reduce separation for people whose appearance varies strongly. The original template set remains the correctness oracle.

## Acceptance
- exact person-level reference remains unchanged;
- prototype table has exactly one row per active person;
- prototype vectors are L2-normalized 512D vectors;
- no duplicate person_id in final results;
- active/model filtering is enforced;
- recall loss is visible and blocks architecture replacement;
- prototype-only and prototype-rerank results are reported separately;
- latency is compared under identical query/gallery conditions;
- no recognition threshold is changed to compensate for retrieval loss.

## Current implementation
`tools/benchmark_pgvector_retrieval.py` already exposes `prototype` and `prototype_rerank` modes and builds a temporary HNSW prototype table. Synthetic vectors are intentionally used to avoid shipping biometric data; they are not evidence of production accuracy.

## Next
Run the full matrix on the real PostgreSQL/pgvector deployment. If prototype recall is insufficient, keep template-level person grouping. If it passes recall/safety gates, benchmark a production-shaped prototype table separately before any schema migration.
