# P1.2.3 — PostgreSQL event persistence + durable idempotency

Status: ACTIVE — implementation complete, integration gate pending

## Objective
Replace the test-only in-memory event store with a durable PostgreSQL boundary while keeping the canonical RecognitionEvent unchanged across HTTP, WebSocket, and MQTT.

## Implemented
- PostgreSQL schema migration: `db/migrations/001_recognition_events.sql`.
- Explicit `EventRepository` protocol.
- `PostgresEventRepository` using an atomic `INSERT ... ON CONFLICT DO NOTHING` boundary.
- In-memory repository retained only as an explicit test double.
- FastAPI HTTP/WebSocket now depend on the repository abstraction.
- Production `app` requires `DATABASE_URL`; tests inject the in-memory repository explicitly.
- Repository unit test covers first insert and duplicate-with-different-payload semantics.

## Verification
- Unit tests cover repository semantics.
- Integration test against PostgreSQL (container/CI service when available) is still pending.
- First insert must return accepted; same event_id with same payload returns duplicate and the original payload.
- Same event_id with a different payload must not overwrite the original event.
- Concurrent duplicate inserts must converge to one stored event.
- Restart/recreate application process and verify idempotency survives because state is in PostgreSQL.
