# P1.2.3 — PostgreSQL event persistence + durable idempotency

Status: ACTIVE

## Objective
Replace the test-only in-memory event store with a durable PostgreSQL boundary while keeping the canonical RecognitionEvent unchanged across HTTP, WebSocket, and MQTT.

## Design
- Store `event_id` as the primary/unique key.
- Persist the canonical serialized event payload plus received timestamp.
- Treat duplicate `event_id` as idempotent: return the already persisted canonical payload.
- Do not perform face inference or manufacture `person_id` in the persistence layer.
- Use an explicit repository interface so SQLite/in-memory can remain test doubles and PostgreSQL is the production target.
- Add schema/index migration before wiring production transport.

## Verification
- Integration test against PostgreSQL (container/CI service when available).
- First insert returns accepted; same event_id with same payload returns duplicate and the original payload.
- Same event_id with a different payload must not overwrite the original event.
- Concurrent duplicate inserts must converge to one stored event.
- Restart/recreate application process and verify idempotency survives because state is in PostgreSQL.

## Completion criteria
- Migration/schema committed.
- Repository implementation committed.
- Unit tests cover repository semantics.
- PostgreSQL integration test passes.
- Concurrent duplicate behavior is deterministic.
- Existing HTTP/WebSocket contract remains unchanged.
